# AGENTS.md — instructions for AI coding assistants working in this repo

Canonical agent-instruction file for any AI tool operating in this repository: Codex, Claude Code (via the `CLAUDE.md` pointer), Cursor, Aider, Copilot CLI, Gemini CLI, and any tool respecting the [AGENTS.md convention](https://agents.md/). Sections are ordered by cost of getting it wrong: invariants and human-sign-off items first; protocols (version bumps, renames) last.

clagentic-lite is a small, deliberate solo-dev coding harness with five gates and two AI roles. Read `README.md` for product narrative, `docs/DESIGN.md` for architecture, `docs/GATES.md` for gate reference.

## Invariants (do not regress; each has a mechanical sweep in `scripts/test_invariants.py`)

Class-level properties, not per-instance bugfixes — each exists because a single reported defect turned out to be one instance of a class recurring anywhere the same shape appears. When fixing a bug or finding, fix the class: (1) one shared primitive/sanctioned path, (2) sweep every existing site via `git ls-files`-driven discovery (never a hardcoded list — see "Sweeping-test discovery convention" below), (3) a guard/sweeping test that catches reintroduction. The only exception is an explicit written deferral with rationale, recorded where the next person will find it.

- **INV-1a — degraded/failed LLM outcomes are never silently reported clean; the timeout mechanism itself never silently no-ops.** `$DS_TIMEOUT_CMD` (`scripts/platform.sh`) must never resolve to a stub that discards its duration and runs unbounded — on a host missing both `timeout` and `gtimeout` it resolves to `ds_timeout_missing`, which refuses to run (exit 99) rather than degrade silently.
- **INV-1b — every `llm-client.sh` call site captures the real exit status AND performs a mode-appropriate degraded check.** (lr-7047bf.) `walk_chain` signals failure via exit status (3=infra, 4=unwrap, 5=turns-exhausted) and via the envelope's own degraded marker; a caller checking only one channel can miss a real failure. Swept by `scripts/test_llm_client_consumer_sweep.py`.
- **INV-2 — constrain the COUNT (or exactly-which) of a matched shape, never merely its presence.** (lr-33958f.) "At least one match" is not "exactly the expected number, proven." Applies to `_llm_unwrap_json_envelope` (locate every fenced-JSON candidate; zero and >1 are distinct failures, never a silent pick), `_llm_json_array_cap`/`_invariant_feed_max_field_chars` (bound at emission), and reviewer/auditor `--allowedTools`/`--disallowedTools` (constrain WHICH tools are available, not a prose note).
- **INV-3 — an accepted-but-unread function parameter is a defect.** (lr-33958f.) Fix by removing it or actually reading it — never leave it accepted-but-silent. `invoke_step`'s ROLE positional was removed once for this; when a genuine reintroduced need appeared, `walk_chain` exports `CLAGENTIC_LLM_CLIENT_TOOL_ROLE` as an env var rather than reopening `invoke_step`'s locked 8-param signature (`test_invoke_step_no_dead_role_positional.py`). `invoke_claude` reads it from env or its renamed 8th positional (`TOOL_ROLE`, not the retired `CALL_ROLE`).
- **INV-4 — every external-process invocation carries an explicit wall-clock bound; every LLM invocation additionally bounds agentic tool use.** No `gitleaks`/`osv-scanner`/`semgrep`/`gh`/`git push`/`claude`/`codex` line in `scripts/gates.sh` may lack a `run_bounded`/`$DS_TIMEOUT_CMD` prefix (the sole entry point, `run_bounded`); every `claude --print` reviewer call carries `--allowedTools`/`--disallowedTools`. KNOWN LIMITATION: this codebase cannot hard-cap agentic turn count — `--max-turns` doesn't exist on the `claude --print` flag surface (SDK-only). Mitigated via wall-clock timeout + tool restriction; turn-exhaustion is detected after the fact via `subtype=="error_max_turns"` and classified as a distinct non-passing outcome (`walk_chain` exit 5, `"turns-exhausted"`). `num_turns` is logged every call (`log_attempt`) so a reviewer near its ceiling is visible in `gates.sh digest`/`status` before it tips over.
- **INV-5 — a Bash-restricted LLM role's restriction is enforced identically across every carrier CLI, and the loud-warning mechanism for a CLI/version this restriction can't reach is driven by the SAME predicate as the restriction, never a hardcoded per-role literal.** (lr-37282a/lr-8a28e0.) `ds_llm_role_is_bash_unrestricted` (`scripts/platform.sh`) is the sole source of truth (currently `gate`/`builder`/`summarizer` unrestricted; `reviewer`/`TOOL_ROLE=auditor` restricted). Both `invoke_claude` (`--allowedTools Read,Grep,Glob --disallowedTools Bash`) and `invoke_codex` (`--disable shell_tool -s read-only`) consult it. `walk_chain`'s per-call warning for an unreachable restriction (old codex version, non-claude/codex CLI) consults the same predicate, not a hardcoded role check — the original class-4 fix's hardcoded `[ "$ROLE_L" = "reviewer" ]` warning gate silently failed to cover `auditor` when lr-8a28e0 moved it onto the restricted side, even though the restriction itself propagated automatically. NOT covered by this invariant: `plugins/clagentic-lite/agents/auditor.md`, the interactive subagent a human invokes directly — its Bash access is Claude Code's own subagent `tools:` frontmatter, a structurally separate mechanism.
- **INV-6 — a `git` call reading repo state (staged diff, branch, SHA, merge-base, ls-files/ls-remote/fetch) must never be bare, and `git -C "$DIR"` alone is not sufficient — every such call must be proven to target the intended repo, not an ancestor.** (lr-da1f28, generalizing lr-4a3f88.) `git -C <dir>` only changes cwd before git's own upward repo-discovery walk runs; when `<dir>` isn't itself a repo but an ancestor is (the wrapper/`.clagentic-project` layout permits this), every repo-state read silently resolves against the wrong repo — a wrong-repo RESULT, not a git error. Highest-stakes instance: `_gate_resolve_fresh_default_branch_ref` feeds `cmd_sast`'s semgrep baseline and `cmd_bleed`'s diff scope — a wrong-repo merge-base there silently narrows a blocking security gate while reporting a clean pass. `scripts/gates.sh` defines `_git_repo_root_is_scoped` (toplevel must canonically equal `REPO_ROOT`) and `_git_repo_scoped_head_sha`; every repo-state call routes through `_git` gated on that predicate, except the two `$DS_TIMEOUT_CMD`-bound fetch/ls-remote calls inside `_gate_resolve_fresh_default_branch_ref` (can't route through a shell function), which gate their whole function body up front instead. `scripts/llm-client.sh`/`scripts/memory.sh` mirror the predicate locally (`_llm_repo_root_is_scoped`, `_mem_repo_root_is_scoped`). `bin/clagentic-lite`'s `_enroll_one` gates the same way so a mis-scoped enrollment can't poison the registry at the source.
- **INV-7 — no tracked, live Claude Code lifecycle hook script or `settings.json` may exist under this repo's own `.claude/` again.** (lr-57db23.) Source of truth is `share/hook-shims/{*.sh,claude-settings}.template`, installer-materialized into `$CLAGENTIC_LITE_HOME/.claude/` at `init`/`update` — never a file this repo commits and Claude Code auto-executes against its own dev sessions. `_stamp_claude_hooks` writes each script validated-then-temp-then-atomic-`mv`. `.claude/commands/recall.md` is a deliberate, documented exception (symlinked directly, no template/stamping — see "Template version-bump protocol"). See "Developing clagentic-lite itself" below for what this means for this checkout specifically.

### Sweeping-test discovery convention

`scripts/` has ~40 test files, most named after the incident that motivated them. A suite organized purely by incident name can't catch a *replicated* defect — a test named after one site never visits its siblings. `scripts/test_invariants.py` is the home for sweeping tests that discover call sites via `git ls-files` (never a hardcoded list) and assert an invariant holds everywhere it's discovered. New class-level invariants belong here first; an incident-named file is for a property that genuinely cannot recur elsewhere.

## What to ask the user before doing

- Adding any new external tool dependency
- Changing the default `BLOCK_SEVERITY` threshold
- Changing the default Builder, Reviewer, Auditor, Merge Gate, or Summarizer CLI
- Modifying the rule list in `pre-bash-guard.sh` or `pre-write-guard.sh`
- Adding anything to the non-goals list in `docs/DESIGN.md`
- Flipping any fail-closed default to fail-open (`CLAGENTIC_ALLOW_MISSING_*`, `CLAGENTIC_MERGE_GATE_BLOCKING`, hook fail-closed-without-jq)
- Loosening the gitleaks allowlist beyond the path + fixture-token intersection

Otherwise, fix what's in front of you and ship it.

## How to behave in this repo

1. **Stay inside the contract.** New features must justify themselves against the five gates (`docs/GATES.md`) and five roles (`docs/DESIGN.md` § "The five roles") — push back before writing code otherwise. The `docs/DESIGN.md` non-goals list is binding: no server, daemon, vector database, embedding model, web UI, plugin marketplace, multi-agent orchestration, or multi-repo state. Propose those as separate projects. **Memory feature bright-line test:** lite may DISPLAY any number the user could verify by eye; it may not let a COMPUTED number decide what's shown. Ordering is permitted only on facts the user authored directly (recency, `source='manual'`) — never a corpus-derived score. Mechanical form: a computed number is lite-legal only if the result set would be byte-identical with the number deleted. (hc-2026-06-01-litemem, tome #552.)
2. **Portability is a hard constraint.** All shell is POSIX sh — no bash-4 features (associative arrays, `${var^^}`, `mapfile`, `[[ =~ ]]` capture groups). Route `sed`/`date`/`stat`/`find` through `scripts/platform.sh` shims (see `docs/PORTABILITY.md`). New shell tool dependency → add a detection block to `bin/clagentic-lite doctor` (`ds_check_tool`) and document it there.
3. **Parameterization is non-negotiable.** Nothing personal/org/host-specific hardcoded. User-supplied values go through `.env` (gitignored), `.env.example` is the committed template. Found a hardcoded value → fix it, or if you can't without breaking flow, mark it `# clagentic-lite:hardcoded` so it greps.
4. **The security gate is local-tool-owned.** `gitleaks`/`semgrep`/`osv-scanner` are the blocking security gates. Never add an LLM call to the blocking path — LLM security commentary is fine only as the non-blocking adversarial layer (Gate 3 extension). This is the product story: "the harness does not trust AI for security decisions" is what makes cross-vendor LLM review credible.
5. **Never edit gate source to bypass a block.** Don't modify `pre-bash-guard.sh`, `pre-write-guard.sh`, or `scripts/gates.sh` to suppress a rule — that removes the protection for every future session. Use the config bypass instead: `CLAGENTIC_ALLOW_BASH_RULES=R-XXX`, `CLAGENTIC_ALLOW_DEFAULT_BRANCH_WRITE=1`, `CLAGENTIC_OSV_SEVERITY=HIGH`, `.clagentic/osv-ignore`, `.semgrepignore`/`# nosemgrep:`, `.gitleaks.toml` path-scoped allowlist, `.clagentic/adversarial-acks.json` (per-CWE structured ack, path-glob scoped, committed/audited — a workflow convenience for trusted contributors, not a security control; protect with CODEOWNERS), `.clagentic/accepted-risks.md` (freetext architectural-risk doc the merge-gate reads to classify a finding as acknowledged; template at `share/accepted-risks.example.md`), `CLAGENTIC_SKIP_UPDATE_ALERT=1`, `CLAGENTIC_ALLOW_STALE_PAYLOAD=1`. Set in `.clagentic/config` or `~/.config/clagentic/config`; document the reason in the commit/PR. Full table: `docs/GATES.md` § "Working around gates".
6. **Cross-vendor is the point.** Builder and Reviewer default to different vendors — a same-vendor reviewer shares the Builder's blind spots. If the user configures both to the same vendor, the install script warns; don't suppress it.
7. **Audit-first.** Every gate decision lands in `.clagentic/lite/audit.db`. New gate → add a `gate_runs` insert. Bypass a gate → log the bypass. The audit trail is the artifact reviewers and InfoSec read.
8. **Read before edit.** Read the full file before modifying it, including hooks and config. No partial reads followed by edits that assume unseen content.
9. **No emojis, no fluff.** Commits, PR descriptions, code comments, log lines: terse, technical, accurate. Match existing tone.
10. **Definition of done: local gate reproduction, not an approximation.** Before reporting complete, run every locally-runnable blocking gate against your branch with its exact invocation — `gates.sh sast`, `gates.sh secrets`, `gates.sh deps`, `gates.sh bleed` (see Gate 4, `docs/GATES.md`) — never a hand-rolled approximation. A red local gate means not done; this repo has no CI, so the local gate is the only check that will ever run. Your completion report MUST include per-gate pass/fail results — omitting them is the same failure as not running the gates.
11. **Class-over-instance: fix the pattern, not the line.** See Invariants above — a silent point-patch of only the flagged line is a contract violation when the same defect shape can recur elsewhere.

## Build / test / run

```sh
# First-time setup (run from the clagentic-lite checkout):
bin/clagentic-lite init            # prereq detection, global config, symlink, plugin install
# Per-project enrollment (run from inside the project you want gated):
clagentic-lite enroll              # init DBs, stamp hooks, register
# Ongoing use:
clagentic-lite gates review        # run cross-model review on staged diff
clagentic-lite gates ship          # run all gates in sequence
clagentic-lite gates digest        # summarize today's audit-db rows
clagentic-lite recall <kw>          # search session summaries
sqlite3 .clagentic/lite/audit.db   # inspect the audit trail directly
sqlite3 .clagentic/lite/memory.db  # inspect session memory directly
clagentic-lite doctor              # verify all prereqs and enrolled-repo hook health
clagentic-lite list                # show enrolled repos with last-gate-run and status
clagentic-lite show memory [N]     # pretty-print last N session memory rows (default 10)
clagentic-lite show gates [N]      # pretty-print last N gate run rows (default 10)
clagentic-lite export              # write self-contained HTML report to .clagentic/lite/report.html
```

There is intentionally no CI. Gates run on the user's machine via git hooks (pre-commit, pre-push) and Claude Code lifecycle hooks — a hosted CI surface would contradict the no-server contract, and the gates exist to block bad changes locally, not to gate PRs against the upstream repo.

**When a gate or hook fails:** don't debug it inline as your own problem. Dispatch the **Troubleshooter** agent (`plugins/clagentic-lite/agents/troubleshooter.md`) first — read-only, tiered diagnosis (Tier 0 triage → Tier 2 deep), returns a root cause plus a `bounce_target` (you, the Builder, or none). Applies to any non-zero gate exit, an unexpected hook error, `gates ship` reporting `BLOCKED`/`INFRA_DEGRADED`, or `doctor`/`enroll` reporting broken state. The Troubleshooter never fixes — it names the cause and stops.

**Iterate the single gate, never the whole chain.** `gates.sh ship` runs the full blocking sequence (secrets, deps, sast, review, merge-gate) in order. When one gate goes red, iterate that gate standalone (`gates.sh sast`, re-run after each fix) until green, then run `ship` once to confirm. Looping the full chain to debug one gate wastes time on gates that already passed (network-bound osv-scanner, an LLM review round) and tells you nothing new.

### Developing clagentic-lite itself

This checkout does not ship a tracked, live `.claude/hooks/*.sh` + `.claude/settings.json` at its own repo root (lr-57db23, INV-7) — a Claude Code session run from this repo no longer self-executes this repo's own hooks/settings by default. Deliberate stop-dogfooding decision: the prior tracked-and-live shape made the source-of-truth and the executed copy the same file, and a future hard-block hook could foot-gun the repo where the tool is developed. Verification is via install + test, not ambient self-execution: run `clagentic-lite init` (or `enroll --self`) against `CLAGENTIC_LITE_HOME=$(pwd)` to materialize hooks and opt this checkout in for the current session; `scripts/test_claude_hooks_materialization.py` proves a template change is byte-correct against a throwaway `tempfile.mkdtemp()` copy without touching the live checkout.

**This is about the product's OWN hooks not self-executing — a different question from how this checkout itself gets built and merged day to day.** That process (who commits, who merges, what's actually running against this tree) is host truth, not product design, and lives in `CLAUDE.local.md` — read that first if you're trying to figure out why a working-tree change happened that you didn't make.

## Template version-bump protocol

Four generated artifacts are stamped into enrolled repos at enroll time and kept in sync by `clagentic-lite update`: `CLAUDE.md` (thin enrollment notice, committed, user-extensible), `.clagentic/lite/builder-contract.md` (full builder rules, gitignored, local only), `.claude/settings.json` (hook wiring, gitignored), `.git/hooks/{pre-commit,pre-push}` (gate shims).

**Hard rule: the committed `CLAUDE.md` contains only the thin notice — never builder rules, agent tables, or gate commands.** Those belong in `.clagentic/lite/builder-contract.md` or `CLAUDE.md.wrapper.template` (local-only, non-git directories). The notice's own language is "if not enrolled, follow normal project workflow"; a rule framed as an unconditional mandate in the committed file contradicts that and misleads non-clagentic contributors. Do not add rule content to `CLAUDE.md.template`.

Each artifact has a version constant in `bin/clagentic-lite`; `update` compares installed vs. constant and restamps only on mismatch. **Any change to a template file requires a version bump to its constant** — without it, `update` sees matching versions and skips the restamp, and enrolled repos never receive the change.

| Template file | Version constant | When to bump |
|---|---|---|
| `share/hook-shims/CLAUDE.md.template` | `CLAUDE_NOTICE_VERSION` | Any content change to the thin notice |
| `share/hook-shims/builder-contract.template` | `CLAUDE_CONTRACT_VERSION` | Any change to builder rules, agents, commands, hooks, gate reference, or `.clagentic/lite/` path references |
| `share/hook-shims/CLAUDE.md.wrapper.template` | `CLAUDE_WRAPPER_VERSION` | Any content change to the wrapper template |
| `share/hook-shims/claude-settings.template` | `CLAUDE_SETTINGS_VERSION` | Any content change to the settings template |
| `share/hook-shims/pre-commit.template`, `pre-push.template` | `SHIM_VERSION` (shared) | Any content change to either hook shim |
| `share/hook-shims/{session-start,prompt-inject,pre-bash-guard,pre-write-guard,post-tool-nudge,stop-summarize}.sh.template` | `CLAUDE_HOOKS_VERSION` | Any content change to any of the six hook script templates (lr-57db23) — materialized into `$CLAGENTIC_LITE_HOME/.claude/hooks/`, so a bump re-stamps the tool's own install, not each enrolled repo directly |

`CLAUDE_MD_VERSION` is retired, replaced by the three narrower constants above; it remains as a tombstone so old installed files still compare correctly. `doctor` warns on any repo still carrying the old `clagentic-claude-md-version` marker; `update` migrates them to the thin notice with a full replace (no old rule content preserved) — if a repo's `CLAUDE.md` still has a rules block after updating, run `clagentic-lite update --restamp` to force a clean restamp. Version strings are arbitrary (`v1`, `v2`, ...), incremented by one each time; the template's own managed-by comment should carry the updated version too (e.g. `clagentic-notice-version: v2`) so the installed copy is self-describing. After bumping, run `clagentic-lite update` (or `update --restamp` to force all enrolled repos regardless of version) — users on older installs get the restamp automatically on their next `update`.

**`.claude/commands/` is different:** symlinked directly from `$CLAGENTIC_LITE_HOME/.claude/commands` into enrolled repos, no stamping, no version tracking. Changes take effect immediately; no version bump needed.

### Single-plugin config-aware render + render stamp (lr-1b5a31)

The `clagentic-lite` plugin (agents + skills, installed globally via `claude plugin install`) is a fifth generated artifact with its own mechanism, not the version-constant table above, because its output depends on live config.

**One plugin, always.** `init`/`update` never install `plugins/clagentic-lite/` directly — they call `_render_clagentic_lite_plugin_dir` first, which reads the checked-in agent files as read-only input and writes a rendered copy to `$CLAGENTIC_LITE_HOME/.clagentic/rendered-plugin/`, injecting `model: role:<role>-chain` into reviewer/auditor/merge-gate frontmatter when router injection is active (`CLAGENTIC_ROUTER_URL` + `CLAGENTIC_ROUTER_INJECT_AGENT_MODEL=1`, and the role's own `CLAGENTIC_<ROLE>_CMD` is non-`claude`), omitting it otherwise. That rendered copy — never the checked-in tree — is what gets registered and installed. Exactly one plugin named `clagentic-lite` exists at any time; a second, differently-named overlay (the pre-lr-1b5a31 `clagentic-lite-router` design) cannot exist by construction. `doctor`'s `_doctor_check_plugin_collision` remains a generic backstop for a *third-party* plugin colliding, not specific to this one.

**Render stamp.** `PLUGIN_RENDER_VERSION` (bump on any change to the render logic — injection point, triple list, plugin.json shape) combines with `_render_config_fingerprint` (every live config knob the render function branches on) into `_render_stamp`, written into the rendered `plugin.json`'s `clagenticStamp` field. **Rule: any new config knob added to the render's branching logic must also be added to `_render_config_fingerprint`** — else a config change that legitimately changes output goes undetected by the stamp comparison. `doctor`'s `_doctor_check_render_stamp_staleness` recomputes the stamp fresh each run and compares to what's installed, advising `update` on mismatch; `update` itself always re-renders/re-installs unconditionally (cheap, idempotent) — the stamp is for doctor's visibility, not to gate whether update runs.

**Migration.** `_migrate_legacy_router_plugin` runs at the top of `_install_clagentic_lite_plugin` (both `init` and `update`), **before** that function's own `claude`-on-PATH early-return, and removes a pre-lr-1b5a31 `clagentic-lite-router` plugin install if found — one `update` run converges any machine to the single-plugin model regardless of prior drift direction. **lr-35315f hardening:** `claude plugin uninstall`/`claude plugin marketplace remove` are package-manager calls, not a filesystem removal — a real enrolled machine was observed left with the legacy plugin's cache directory still present and marked *orphaned* by Claude Code's own plugin manager (not removed), and an orphaned-but-present entry remained *resolvable* by the agent resolver, shadowing the correct base-plugin copy. The migration now also removes `$_LEGACY_ROUTER_PLUGIN_CACHE_DIR` (`$HOME/.claude/plugins/cache/clagentic-lite-router` — a FIXED path built only from `$HOME` plus hardcoded literal segments, never interpolated from config/env, per BOBBIE's PR #164 safety constraint) directly, and that removal runs unconditionally rather than being gated on `claude plugin list` still mentioning the legacy name — an orphaned entry can drop out of that listing while its cache directory remains on disk and resolvable, which is exactly why the un-hardened migration never fired on the affected machine. **A second layer of the same conditional-convergence defect (PEACHES, PR #179 review, rule amos.path-choice.4):** the cache-directory removal inside `_migrate_legacy_router_plugin` was itself unconditional, but its only real dispatch call site, `_install_clagentic_lite_plugin`, used to gate entry to the whole function (migration call included) behind its own `command -v claude` check — so a machine with no `claude` binary on PATH never reached the migration at all. `_migrate_legacy_router_plugin` is now called before that guard; only the plugin-manager calls remain internally gated on `claude`'s presence. `doctor`'s `_doctor_check_orphaned_router_plugin` reads the cache directory directly (not `plugin list`, and not gated on `claude` either) and FAILs when a resolvable agent file carrying a `model: role:*-chain` override is found there.

## Plugin rename protocol

If a plugin is renamed, `cmd_update`'s installed-check uses an exact-token grep (`grep -qE '(^|[[:space:]])<name>(@|[[:space:]]|$)'`), so the old name won't match the new one — update falls through to `plugin install` (correct for a fresh install) but leaves the old plugin installed alongside the new one. **Rule: any plugin rename requires an explicit migration step in both `cmd_init` and `cmd_update`:** (1) before the installed-check, detect the old name with the same exact-token grep; (2) if found, uninstall it (`claude plugin uninstall "<old-name>@clagentic-lite"`, fallback to bare `"<old-name>"`); (3) proceed with the normal install/update path. The migration block stays permanently — it's a no-op once the old name is gone, and removing it breaks users who skipped intermediate versions.

**Plugin manifest `skills` field:** Claude Code discovers skills from a plugin's `skills/` subdirectory automatically (same convention as `agents/`). Do not add a `skills` array to `plugin.json` — not in the supported schema, and it will fail `plugin install` entirely, blocking agent delivery too.
